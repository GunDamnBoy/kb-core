# Podcast 知識庫摘譯｜什麼是對的產出

這份文件只回答一件事：**今天這一版，怎樣算對。**

怎麼做出來在 `scripts/podcast/DIGEST-PROMPT.md`；每集撰寫的眉角在 `scripts/podcast/preamble.md`；
每一個數字在 `podcast/anchors.json`；節目清單與優先序在 `scripts/podcast/shows.json`
與 `config.json`。**本檔一個數字都不抄，節目清單更不抄** —— 抄本會過期。

---

## 一、這個站是什麼

把每天沒時間聽完的頂級財經 Podcast，變成**可以在手機上讀完的完整中文摘譯**。
每天（含週末）偵測新集數 → 取得全文逐字稿 → 每集產出繁體中文完整摘譯與核心重點 →
發布到 GitHub Pages，同時交付一份 Word 報告。

定位是個人知識管理與研究輔助，**非投資建議、不做公開發行**（全站 noindex）。

**它是完整摘譯，不是摘要。** 讀者讀完應該不需要再去聽那一集。

## 二、每天產出的是資料，不是網頁

一天一個檔，`data/<date>.json`；當日加進 `data/index.json` 的 `days` 最前面（一律由新到舊）；
回訪並寫回帳本。**`index.html` 不要動。** 歷史完整累積、不刪不改。

**當日 0 集時不產生空檔案、不動 `index.json`、不產 Word 報告**，直接回報後結束。
0 集是一個合法的結果，但它要先通過外部對照（見第六節）。

### 日期檔的形狀

頂層：`date`／`label`／`generatedAt`／`crossCut`／`postscript`／`episodes`。

每集：`id`／`showKey`／`show`／`title`（`節目名｜標題`）／`meta`／`published`／`hosts`／
`guest`／`source`／`url`／`chars`／`summary`／`guests`／`topics`／
`quality{completeness,status,speakerNote,timestampNote}`／`takeaways`／`sections`／`quotes`。

- **`showKey` 一律取自 `shows.json`。** 在網站端另取一套，徽章永遠對不上。
- **`chars` 由組檔時的 python 機械覆寫**，定義在 `anchors.json` 的 `char_definition`。
  **不是為了精確，是為了讓所有集數用同一把尺。**
- **`topics` 只能從受控詞表選**（在 `anchors.json`）。
- **`quotes[]` 三個欄位：`speaker`／`original`／`text`。** `original` 是逐字稿裡的原句、
  一字不改（含原文語言），`text` 是中譯。

  `original` 存在的唯一理由是**它讓「金句是不是編的」變成機械可判** ——
  組檔時拿它回去對逐字稿做子字串比對，對不上就整條丟掉並具名記錄。
  少了這個欄位，「金句必須是逐字稿裡實際出現的發言」就只是一條靠自覺的規則，
  而**依賴自覺的紀律不是紀律**。2026-08-20 首輪 63 條金句全部通過比對。

  比對用**子字串包含**，不要用整行相等 —— Bloomberg 有幾行的講者標籤是
  `Speaker 6]`（右方括號不是冒號），整行比對會把完整的發言誤判成對不上。

### 逐字稿住在 repo 外面

`~/podcast-transcripts/<date>/`，YAML front matter ＋ `[MM:SS] 講者：內容` 正文。

**這是版權界線，而且是結構性的**：那個目錄不在任何 repo 的工作區內，
也沒有任何程序會 push 它 —— 不是「靠紀律不要移進去」。**Word 檔同理。**

## 三、四層退援

順序與各層的規則在 `anchors.json` 的 `fallback_order`。三件事比順序本身更重要：

- **manifest 決定「有哪幾集」，不決定「用哪份全文」。**
  A 類節目即使 podfetch 已經轉錄，仍然要去抓官方稿 —— 官方稿沒有廣告、沒有口頭贅語，
  同樣片長多出三到五成實質內容。抓不到才退回，並**據實填 `source`**。
- **退到哪一層要寫在資料裡。** `source` 是讀者判斷可信度的依據，也是維護時看得見的訊號。
- **FT 失效時退回 podfetch，不是跳到 YouTube。** 跳層會讓一個可用的來源被跳過。

## 四、篇幅

分層表、字數定義、段數換算全部在 `anchors.json` 的 `length_tiers`。

三件關於它們的事，**比數字本身重要**：

- **先估篇幅再落筆，不要寫完再壓縮。** 這是**成本規則**不只是文風規則 ——
  每重寫一輪，整份逐字稿就重新進場一次。骨架階段發現內容量遠超上界時，
  **砍章節深度或合併次要主題，不是寫完再刪**。
- **不要為了壓進區間而砍掉整段論點**；反過來，**短節目硬拉長比長節目超規格更嚴重**。
- **規劃用段數、計量用 python。** 自報的字數不可信。

## 五、每集要有什麼

數量全部在 `anchors.json` 的 `per_episode`。

- **核心重點必須含對投資人的含義** —— 只複述節目講了什麼不算重點。
- **金句必須是逐字稿裡實際出現的發言**，中譯並標明講者。**沒有逐字稿就不寫金句。**
- **講者標記保守優先。** 看到 `Speaker N` 是誠實而非失敗。
  判定不了就寫節目名，**不要猜人名** —— 錯的名字會變成對真實人物的不實陳述，
  比沒有名字糟得多。
- **重播照常完整摘譯**，但 `published` 填**原始播出日**、`source` 寫明是重播。

## 六、0 集要先證明它是真的 0 集

**日誌說「沒有新集數」不可以就此收工。** 快取過期時的日誌與真正的 0 集日**一模一樣**。

必做外部對照：用高頻節目（AppleID 在 `anchors.json`）帶 cache-buster 查一次。
`stale_feed_hours` 的健全性檢查**只認得「所有節目同時安靜」這一種形態** ——
**看不到警告也還是要做外部對照。**

2026-08-15 的量級是：整整一天回報「沒有新集數」，實際有 10 集。

## 七、成功與當期失敗

**成功一句話**：早上打開它，能讀完昨夜幾檔頂級節目的完整內容而不必再去聽，
而且幾天後回頭看得到當初丟出去的觀察點兌現了沒有。

**當期失敗判準（機械可判，任一成立即當期失敗）**：

1. 有集數的 `chars` 落在它所屬層級的區間外，且沒有具名的下界例外記錄
2. 有集數的 `topics` 不在受控詞表內，或數量超出範圍
3. 當日集數 ≥ 門檻卻沒有 `crossCut`
4. 帳本沒有新增觀察點，或有逾期未判的項目
5. `index.json` 的 `days[0]` 不是當天，或執行時間戳沒動

第 4 項是本站與一般摘要的分水嶺 —— **拋出去的觀察要回頭對答案**。

## 八、帳本

觀察點是 `ledger-v1` 的一個實例。收錄標準只有一條，寫在 `anchors.json`：
**這句話三個月後有可能被證明是錯的嗎？不能就不要收。**

免責聲明、來源標註、管線自檢、純敘述性總結都不是觀察點。

**開帳之後不得改寫。** 判定到期由哨兵開 issue。

## 九、合規

1. **逐字稿與 Word 檔不進任何 repo。**
2. **摘譯是濃縮中譯，不是逐字轉載。** 付費來源尤其只做重點濃縮並附連結。
3. **每集保留來源標註與原文連結**，鼓勵前往原始節目收聽。
4. 全站 noindex。明確標示非投資建議。
5. **不代為登入任何服務。**

## 十、回報要記什麼

退到第幾層與原因、下界例外的具名記錄、`DEGRADED` 的集數與**真正的成因**
（跳針／掉字／截斷 —— 語速基準只決定分母，不是候選答案）、
外部對照的結果、以及任何被跳過的集數與理由。

**回報是自述，不是查核依據。** 查核一律讀資料本身。
