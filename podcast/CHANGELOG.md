# Podcast 知識庫摘譯｜沿革與維護判斷

給**維護者**讀，不進執行路徑。記事故經過、當初為什麼這樣決定、**被否決的選項**。
每一筆五欄：動到哪些檔／量測／怎麼驗的／怎麼倒回去／當時已知的風險。

---

## 維護判斷

### 規則有了執行者才算數

同源推送那次事故的修法不是「寫一條規則」，是**指定由誰在第幾步寫那個欄位**。
一條沒有執行者的規則，跟沒有這條規則的差別只在文件長度。

### 依賴自覺的紀律不是紀律

「低於下界要回報」如果只寫成期待，就會在最需要的時候不發生。
所以它被寫成 `preamble` 的**必答項** —— 執行者不回報就是漏了一個欄位，看得見。

### 節目專屬的處理方式，只要第二檔也適用，就升成通則

重播的 `published` 填原始播出日，原本是某一檔的特例；
第二檔節目出現同樣情況時就升為全庫規則。**特例累積成的規格會互相矛盾。**

### 規格天天被違反就不是規格

單一字數區間改成四層分層的理由。長節目壓進短區間必然砍掉整段內容，
而那是**每天**在發生 —— 該改的是規格，不是繼續要求執行端「盡量」。

## 2026-08-19｜重寫：四份文件 ＋ podfetch 進版控

**動到哪些檔**　新增 `podcast/BRIEF.md`、`podcast/anchors.json`、
`skills/podcast/SKILL.md`、`scripts/podcast/preamble.md`、本檔。
`podfetch` 由 `~/.podfetch` 移入 `scripts/podcast/`（**原樣移入，不改邏輯**）。

**量測**　（待第一輪實跑後補）

**怎麼驗的**　與投顧同一套：拿舊規格卡的「必須原封保留」清單逐條做覆蓋稽核。

**怎麼倒回去**　舊的 `AGENT_BRIEF.md` 與排程 prompt 在 Google Drive 的規格保存包；
`podfetch` 移入後 `~/.podfetch` 的原件先不刪。

**當時已知的風險**　`podfetch` 原樣移入代表它**還沒有底盤的具名退出碼與檢查**，
只有一層適配。它身上那幾條用事故換來的邏輯（跳針剔除、雙訊號時間戳判定、
0 集健全性對照）目前只有程式碼在保護，沒有 fixture。

### 四個重寫決定

**1. `podfetch` 原樣進版控，不重寫。**
它是六套系統裡唯一真正的生產程式，零外部相依，而且已經被除錯得最徹底。
同一輪既換架構又換轉錄管線，壞掉時無法歸因 —— **一次只動一個變因**。

**被否決的選項**：照底盤契約整支重寫。誘惑是「一次做對」，
代價是把失敗模式最多的一支放在變動最大的一輪裡。重寫另開工單。

**真正的動機不是重寫，是版控**：那支程式從來不在任何 repo 裡，
而我們今天才親眼看過「Mac 上跑的跟版控裡的不一樣，沒有任何東西會發現」。

**2. A 類官方逐字稿的抓取搬到 Actions（FT 除外）。**
八檔裡只有一檔需要 Chrome。搬過去有一個具體收益：
**`web_fetch` 的字元上限會靜默截斷不報錯**（實例：某集只取到 73%），
而 Actions 裡沒有這個上限。**那個坑不是被繞過，是不存在了** ——
跟投顧那邊「Chrome 的 CORS 與 JSON 下載」同一個形狀。

**3. 觀察點記分板升成 `ledger-v1`。**
它本來就是一本訊號帳本：有收錄標準、有五種判定值、要回訪。
接上去之後，投顧哨兵裡那條 `sentinel.ledger_overdue`
就從 SKIPPED 變成真的在看。

**4. Word 報告保留，但改成 publish 成功之後才產。**
從**已發布的** JSON 機械轉出。這樣不會出現「Word 有這集、網站沒有」。
它不進 repo —— Public repo ＋ 付費來源全文 ＝ 著作權問題。

## 從舊規格帶過來的待決

### `podfetch` 的四項設定只能人工比對

兩個布林值（healthcheck 的數值比對抓不到）＋兩個清單型設定。
**待決**：這四項要不要改成由檢查程式讀 `config.json` 驗證。
現況是「有人記得去看」，而那不是機制。

### 時間戳檢查的三個盲區沒有補

回跳、同段重複、相異時間戳少於五個。
單調性檢查**實測後決定不加**（全庫 91 集有 32% 出現回跳，遠超雜訊門檻，
初判「單調遞增在正確合併的逐字稿裡恆真」被量測推翻）。
另外兩個目前只靠 `preamble` 要求撰寫者主動回報。

### 語速基準有兩檔未校準

沿用全域值，所以它們的完整度可能系統性偏低 ——
**那是基準問題不是缺字**，但目前分辨不出來。

## 2026-08-20｜第一晚實跑：10 集全 OK，兩個門檻是它教出來的

**動到哪些檔**　`podcast/anchors.json`（新增 `episode_admission`、`quality.completeness_high`）、
`scripts/podcast/patch_shows.py`（sharptech 除名）。

**執行**　01:00 起跑、01:13 收工，7 檔節目 10 集，`status` 全 `OK`，沒有 FAILED。
視窗 `08-17 17:00Z → 08-19 17:00Z`。切段全部走 pure-python——**ffmpeg 刻意不裝的決定
在這一晚得到實證**，10 集沒有一集因為切段出問題。

**sharptech 除名。** 加它的時候只看了節目影響力，沒有看 feed 內容：Apple 公開 feed
的每一集標題都帶 `(Preview)`，完整集在訂閱者私有 RSS。

**它為什麼不會被現有的東西抓到**　預告片會被忠實轉寫、`status` 是 `OK`、完整度大概
100%——因為完整度量的是「轉寫得完不完整」，不是「這是不是那一集」。
**指標對它是瞎的**，所以擋它的那一層要放在指標之前，這就是 `episode_admission`。

**時長下限不能設全域。** 當天最短的兩集是 bloomberg 22.1 分、unhedged 22.9 分，
都是正常完整集。所以主判準只能是標題標記，時長 10 分只是第二道，
而且它擋不住一支 12 分鐘的加長預告——**這個限制要寫下來，不要讓下一個人以為它擋得住。**

**完整度有兩側，而規格原本只防低的那側。** 當天 iltb 是 **1.57**。
我去驗了逐字稿：最長連續重複只有 2 個 token、3-gram 分佈正常，**不是跳針**
（跳針本來就在計字前剔除了，08-08 那筆事故的修法還在生效）。
剔除跳針之後仍然偏高只剩一個解釋：**那個節目的語速基準過期了**——
iltb 實測約 224 字/分，而 `shows.json` 記的是 140。

於是 `completeness_high` 該叫的是「去修分母」，不是「逐字稿有問題」。
**同一個數字的兩側是兩種病，不要用同一句話描述它們。**

**當時已知的風險**　`title_reject_markers` 是字串比對，節目換一種標法就漏。
它擋的是已知的形狀，不是所有形狀——真正的保險是每天有人看得到「今天收了幾集、
哪幾檔零集」，而那個還沒有。

**通則**　**指標量的是它量得到的那一維，不是你關心的那一維。**
「轉寫得完不完整」與「這是不是那一集」差一個維度，而低維的那個永遠先給答案。
這跟保底層那次（「讀得開」不是「有資料」）是同一條，只是換了一個位置出現。

### 檢查落地：只寫取數層，日報層刻意留白

`checks/podcast.py` 十條，全部驗 manifest。**日報那一層沒寫**——門檻雖然已經在
`length_tiers` 與 `per_episode` 裡，但 doc 還沒有一份真的樣本。

憑 anchors 想像 doc 的欄位去寫，寫出來的會通過 selftest，然後在第一天對著真實的 doc
全部 SKIPPED 或全部誤判。**那種檢查比沒有檢查更糟，因為它會綠。**

十條對著今早那份真 manifest 跑：**9 PASS · 1 WARN · 0 FAIL**。
唯一的 WARN 正是 iltb 的 1.57，而訊息說的是「去修 shows.json 的 wpm」
而不是「逐字稿有問題」——上界那一側的成因寫進了訊息裡。

**已知缺口（補不了在檢查這一層）**：`episodes` 是空的時候，manifest 分不出
「今天真的沒有新集」與「查詢壞了」。podfetch 只記總數（`找到 10 集`），
不記每一檔查了什麼、回了什麼。要補這個洞得改 podfetch 的輸出，
**沒有那份資料就寫不出那條檢查**，所以寫進 `manifest_wellformed` 的 blind_to 而不是假裝有。

## 2026-08-20 下午｜第一份日報，以及一個判斷錯誤

十集全跑，40,298 字、3 條交叉線、3 個觀察點。篇幅全部落在層級區間內、
topics 全在受控詞表、63 條金句機械比對 **0 條對不上**。

### 我早上的診斷是錯的

看到 iltb 完整度 1.57，我查了「最長連續重複同一 token」（只有 2）與 3-gram 分佈
（正常），據此宣告成因是**語速基準過期**，還把這句話寫進了 anchors。

實際成因是**整段內容重播兩次**：`[35:30]–[39:58]` 在 `[40:00]–[44:58]` 與
`[45:00]–[49:31]` 各完整重播一次，970 token。

**區塊重複的 3-gram 分佈本來就正常，因為重複的是一大段連貫文字。**
我用測 A 的方法宣告了 B 不存在——而那個宣告聽起來很有依據，因為我確實跑了程式。

### 第二個發現讓它更嚴重

bloomberg 8/19 完整度只有 **0.81**，一樣有 281 token 的區塊重播，
而且那段重播**覆蓋掉了下一位來賓訪談約 3.5 分鐘的真實內容**。

所以：**重播疊加時完整度上升，重播覆蓋時完整度下降。**
`completeness_high` 只抓得到前一種，而後一種才是有東西真的不見了的那一種。
十集裡三集有區塊重複，檢出率 30%——不是邊緣情況。

### 門檻是量出來的，不是訂出來的

12-gram、位置連續合併成區塊，十集實測的分佈：

| 形態 | token 數 |
|---|---|
| 台呼、廣告讀稿 | 40–79 |
| 片頭預告（cold open） | 112 |
| **真實的區塊重播** | **281、959、970** |

下限取 **150**，因為 112 到 281 之間有 2.5 倍空隙。片頭預告另外用
「第一次出現落在前 200 token」豁免——**那是片頭預告的定義本身**，
不是為了讓數字好看而開的例外。

allin 那集也有區塊重複，但是**同義重述不是逐字**，機械查重完全看不到。
那條寫進 blind_to，不假裝抓得到。

### 偵測放在哪

`tools/podcast_verify.py` 算、`checks/podcast.py` 判——檢查不做 IO，
跟 `watch_sentinel.py` 的 `code_drift()` 是同一道 seam。門檻在 anchors，
所以調門檻不用改程式。

### 十集共通的兩件事

**講者標記幾乎每一集都不可靠**：編號互換、同一人多編號、主持人與來賓對調。
十個撰寫 subagent **全部**自主退回保守標記——preamble 第四節今天被驗證了十次。

**時間戳問題普遍，而 front matter 的 `timestamp_notes` 幾乎都是空的**：
回跳、溢出、整整 10 分鐘位移、歸零重計，還有一個「假結尾」
（All-In 第一段有完整的道別詞，但節目還有四十分鐘）。
那個檢查只認得兩種形態，實測十集漏掉絕大多數。**空的 timestamp_notes 不是好消息。**

### 通則

**「我查過了」與「我查對了東西」是兩件事。**
跑過程式不等於測到了那個現象——我的方法對 A 敏感、對 B 全盲，
而輸出長得跟「沒問題」一模一樣。

這跟保底層那次（讀得開 ≠ 有資料）、跟 lock 那次（差集不等於成因）是同一族：
**每一個否定結論都要問一次「我這個方法測得到它嗎」。**

## 2026-08-20 下午｜第一次走完發布路徑，以及底盤被第二套系統戳破的一個洞

`podfetch 01:00 → 手動日報 → ~/outbox/podcast/ → publish → GitHub → Pages`，
整條鏈第一次跑通。回執 `exit 0 @ pushed`、commit `102ab77`，
**線上驗過**：`days[0].date = 2026-08-20`、`episodeCount = 10`、20 天、
`updated` 與回執時間對得上。

**回執說 pushed 不等於網站上有** —— 這條要每次都回頭看一次線上的檔案，
不是看回執就收工。

### 底盤的洞：`index_entry` 寫死了投顧的形狀

`publish.py` 裡的 `index_entry()` 產的是 `weekday`／`stamp`／`headline`／`cards`／
`thermo`／`threads`／`watch`／`pulse`／`snap`。podcast 的 doc 沒有 `overview`，
publish 會在組 entry 時直接 KeyError。

系統登記那道接縫管到了「跑哪組檢查」與「payload 怎麼組」，
**漏掉了「index entry 長什麼樣」**——而那同樣是每套系統各不相同的東西。

**第一套系統不會發現這種洞，因為它就是那個形狀。接縫漏一個維度，
要等第二個使用者才看得見。**

修法是把 `index_entry` 變成 `System` 的第三個欄位，而且**必填、不給預設值**——
`systems/tracer.py` 立刻報 `TypeError`，那正是要的效果：退回預設會讓 podcast 的
索引長出五個永遠是空的跨日欄位，而**空欄位跟「有欄位但沒填」在資料上長得一樣**。

### 一條判準在資料裡找不到欄位

寫 `podcast.chars_in_tier` 時發現：**doc 裡沒有任何欄位存得下片長**。
`published` 是「2026年8月18日｜片長 56 分鐘」這種給人讀的字串，
而層級是由片長決定的——所以 BRIEF 第七節第一條判準當時是判不了的，只是看起來像。
加了 `minutes` 欄位。

跟投顧那次保底卡的 `base` 欄位完全同一件事。

### 13 處違規，成因在派工單不在撰寫端

`podcast.per_episode_counts` 第一次跑就抓到 13 處：`anchors` 的重點與金句上界都是 5，
撰寫端寫了 6 到 8 條。**不是撰寫端貪心，是我的派工單沒把數量寫進去**，
JOB.md 只給了 schema。檢查抓到的是派工的缺漏。

處置：**修剪到符合門檻，不調高門檻。** 為了讓今天過而改 anchors，
正是這整套一路在防的事。

但張力要記著：Bloomberg 那集有四段獨立訪談，8 條重點是有實質內容的不是灌水。
`[3,5]` 是舊系統帶過來的、今天第一次遇到真實產出。
**要動它得等有量測依據，不是因為它今天擋了東西。**

### 兩個沒補的洞（寫進 blind_to，不假裝抓得到）

- **逾期未判的觀察點**：BRIEF 列為當期失敗判準，但帳本 65 條沒有到期欄位
  （歷史 62 條只有 date／status／verdict）。要補得先加 `due`，
  而歷史不改寫——只能從新項目開始帶。
- **`crossCut.points[].episodes`** 沒有回頭比對是不是當天真的有的那幾集。

### outbox 分目錄

podcast 的草稿放 `~/outbox/podcast/`。`publish.py` 的 `glob("*.draft.json")` 非遞迴，
所以投顧那條線（掃 `~/outbox/`）一個字都不用改。
**更根本的解是草稿自帶 `system` 欄位、publish 讀出來比對**，
等下次改投顧 SKILL 時一起做，不要現在同時動兩個變因。

## 2026-08-20 傍晚｜官方稿層的偵查：六檔沒有共用規則

`fallback_order` 第一層還沒接。這一節是**偵查結果**，不是實作——
寫下來是為了下次不用重跑這五輪測試。

### Apple lookup 回得出 `feedUrl`，六檔皆然

所以 `shows.json` 只要維護 `appleId`，**feed 網址不用存第二份**。
`https://itunes.apple.com/lookup?id=<appleId>` → `results[0].feedUrl`。

### 但 RSS 的 `<link>` 不等於「那裡有逐字稿」

| showKey | RSS `<link>` | 那個頁面 |
|---|---|---|
| acquired | `acquired.fm/episodes/…` | 節目自己的站，**未驗證** |
| dwarkesh | `dwarkesh.com/p/…` | 25,725 words、**0 個 `Name:` 輪替**、18 個時間戳 |
| latentspace | `latent.space/p/…` | 1,432 words → 付費牆或 JS |
| macrovoices | `macrovoices.podbean.com/e/…` | **Podbean 播放頁**，199 words |
| mib | `omny.fm/shows/…` | **Omny 播放頁**，293 words |
| gsx | **沒有 `<link>`** | 只有 megaphone 的 MP3 |

兩個代管平台（Podbean、Omny）的播放頁只有節目說明。
**「RSS 有連結」與「那裡有稿」是兩個不同的問題**，而第一個問題答對了會讓人以為第二個也答了。

### GS：slug 可推導但只通 3/10

`.../goldman-sachs-exchanges/<標題 slug>`。最近十集實測 **3 通 7 個 404**，
成功的三集標題都長，404 的清一色是短標題。索引頁 569KB 但**零個 episode 連結**——JS 渲染。

**處置：不逆向工程它的渲染，改做機會性嘗試。** 試 slug，200 且輪替 ≥ 20 就用，
404 就退回第二層並在 `source` 具名記錄。**這跟硬鑽是兩件事——它的失敗是 404，
響亮、即時、沒有歧義**，而硬鑽出來的 scraper 壞掉時會安靜地退回第二層，
跟「本來就沒有官方稿」長得一模一樣。

### 我的偵測方法自己就是錯的

用 `\b[A-Z][a-z]+ [A-Z][a-z]+:\s` 數講者輪替，在 acquired 那頁量到 **1543 次**，
判成「有逐字稿」。實際上抓到的開頭是
`Disney: … | Acquired so Cloudflare URLs win cascade before parses and triggers…`
——JS 設定字串漏進來被當成講者標記。

**今天第三次撞到同一條：我的方法對 A 敏感、對 B 全盲，而輸出長得跟答案一樣。**
（前兩次：以連續 token 重複判區塊重播、以 diff 判 lock 的差集成因。）

下次要用的判準不是 regex 計數，是**抽出來的文字與 podfetch 稿的相似度**——
兩份講同一集，重疊度應該很高；重疊度低就表示抽到的不是那一集的內容。

### 價值重估：官方稿的好處在講者歸屬，不在字數

BRIEF 寫官方稿「同片長多出三到五成實質內容」。**GS 這一集不成立**：
去標籤後 8,338 words，扣掉導覽與訂閱樣板之後跟 podfetch 的 7,551 差不多。
原因是 GS 的稿是編輯過的，拿掉了 "um"、"you know" ——字數沒變多，密度變高。

真正的好處是 **60/59 乾乾淨淨的講者輪替**，而 2026-08-20 十集實測
podfetch 的講者標記幾乎每一集都不可靠（編號互換、同一人多編號、主持人與來賓對調）。
**那是 podfetch 這條路補不起來的東西。**

但當天十集裡只有兩集是 A 類。所以這一層每天的實際收益是「兩集的講者標記變準」，
而成本是六種各自不同的路由。**它該獨立排一次、一檔一檔做**，
不是在別的工作做完之後順手推完。

## 2026-08-20 傍晚｜排程有兩種，我用錯了那一種

日報那一段接上「Cowork 排程」時，我建的是**雲端排程**（`create_trigger`）。
排在台北 03:06，指令寫得很完整。

然後我做了一件事：**在它明天真的跑之前，先用唯讀探測跑一次。**
指令改成「只確認碰不碰得到那四個資料夾，不要寫任何東西」。

結果是決定性的：

> `mcp__remote-devices__*` 這組工具在那個 session 裡**根本不存在**。
> `ToolSearch` 精準查詢回 `No matching deferred tools found`。
> 雲端側 `ls /root/mnt/` → No such file or directory。

**不是斷線、不是缺授權、不是等一下會好 —— 橋不在那裡。**
由雲端排程啟動的 session 一律不接 desktop bridge。重試多少次都一樣。

### 正確的機制是桌面 app 自己的排程

舊系統的 `AGENT_BRIEF` 寫得很清楚，而我沒有先去讀它：

> `03:00` — Cowork 排程 `podcast-digest-daily`（cron `0 3 * * *`）
> **排程只在 Claude 桌面 App 開著時執行**，App 關閉時錯過的會在下次啟動補跑。

還有資料夾那條的解法：

> 連線不保證跨工作階段留存，失敗的樣子和「podfetch 沒跑」一模一樣。
> 讀不到就先自己連：`mcp__cowork__request_cowork_directory`，
> **無人值守下實測不會跳核准對話框。**

**兩種排程長得像同一個東西，能力完全不同。** 桌面排程是本機程序，
檔案直接讀；雲端排程是遠端容器，只有在互動 session 裡才有橋。

### 代價（桌面排程的三條）

- 桌面 app 必須開著（Mac mini 已設 `sleep 0`，app 開著放就行）
- 錯過的會在下次啟動補跑 —— 是延後不是漏掉
- 資料夾連線要在指令第一步自己重連

### 通則

**「同名的兩個東西能力不同」是一種特別難防的錯**，因為兩邊的文件、術語、
甚至工具名稱都長得一樣，而失敗要到真的執行時才出現。

擋住它的不是更聰明的推理，是**在它真的要跑之前，先用唯讀的方式跑一次**。
成本是一次觸發，回報是提早一晚知道整條鏈接不上。

這條跟今天早上那次是同一族：`git log -S` 問「哪個 commit 改變了這個字串的出現次數」、
`--selftest` 的兩側夾擊、金句的 `original` 回稿比對 ——
**都是把「我以為會怎樣」換成「我讓它先做一次給我看」。**

## 2026-08-20 夜｜補舊規格的四條判斷，順手發現兩個「看起來有、其實沒有」

四條裡有三條是純粹寫進 `anchors.json`，第四條是先修程式再寫。
真正值得記的是後面兩個對帳結果 —— **兩個東西都存在、都寫得好好的，但都沒有在保護任何東西。**

### 一、`podcast_docx.py` 的集數守衛，寫好之後永遠不可能成立

它長這樣：

```python
written = 0
for e in eps:
    written += 1        # ← 迴圈頂端，無條件
    ...
if written != expected:  # expected = len(eps)
    return 10
```

`written` 恆等於 `len(eps)`，`expected` 也是 `len(eps)`。
**這條守衛看起來在數集數，其實只是在數迴圈跑了幾圈。**

昨天我為它寫過一次負向測試，測試本身也是壞的（把改壞的檔寫到 `2026-08-19.json`，
卻對 `2026-08-20.json` 呼叫 `build()`）。兩層錯誤剛好互相掩護：
測試沒測到東西，而它「通過」了，於是守衛看起來是好的。

修法是把 `written` 的定義換一個維度 —— 從「迴圈圈數」換成「文件真的多了字」：

```python
d.add_paragraph(e.get("summary", ""))
body_from = len(d.paragraphs) - 1
... takeaways / sections / quotes ...
if sum(len(x.text.strip()) for x in d.paragraphs[body_from:]):
    written += 1
```

界線刻意取「有沒有字」而不是「幾個字」：空殼是 0，任何一集正常內容都遠大於 0，
**中間沒有需要調的門檻**。字數夠不夠是 `chars_in_tier` 在發布前的事，不是這裡。

這次的驗收拿**已發布的那一份** `data/2026-08-20.json`（先比對 md5，我手上那份是 trim 之前的舊快照）跑三種情形：

| 情形 | written / expected | 退出碼 | 位元組 |
|---|---|---|---|
| 原樣 | 10 / 10 | 0 | 120,046 |
| 挖空第 2、5、9 集的內容欄位 | 7 / 10 | 10 | 101,517 |
| `episodes` 混進一個空 dict | 10 / 11 | 10 | **120,109** |

第三列是重點：**120,109 bytes 遠在 `size < 20_000` 之上**，
所以位元組守衛對「少一集」是全盲的 —— 這正是集數守衛存在的理由，
而它先前不存在，只是看起來存在。

### 二、`fwdguidance` 的徽章沒有顏色

寫 `shows_lifecycle` 那條時順手對了一次帳：`shows.json` 21 檔現役，
`index.html` 26 組配色。差集兩邊都看：

- CSS 有、現役沒有 → `capitalallocators`、`bg2`、`breakdowns`、`lennys`、`lex`、`pivot`
  —— 這是**對的**，舊日檔還在站上，刪了就掉色。
- 現役有、CSS 沒有 → `fwdguidance` —— 今天早上加的，三條規則全漏。

舊規格只寫了「移出時 CSS 保留」，**沒有人寫反過來那一邊**，
因為移除是有人在盯的動作，新增卻是「加一行 JSON 就好了」。
徽章缺色不會丟出任何錯誤，只會在那檔節目第一次出集數的那天默默沒有顏色。

補上三條（`.ep.s-fwdguidance`、`.b-fwdguidance`、深色覆寫），
主色 `#7a3760` 是拿現有 26 色在 HSV 空間算最遠點挑的，不是隨手選的 ——
26 檔之後憑眼睛已經挑不出「還沒被用過」的顏色。

**連帶陷阱**：`publish` 只做 `git add data`，改 `index.html` **不會**被排程順手帶進去。
`.kb-data-repo` 就是這樣漏掉整整一天的，這次要另外提交。

### 三、`podcast_verify.py` 的 11 條檢查，沒有任何東西在呼叫它

`grep -rn podcast_verify` 全庫只有兩處，都在文件裡。四個 `launchd` 工作跑的是
`podfetch.py`、`publish.py` ×2、`watch_sentinel.py`。

所以現況是：

- **doc 層 6 條**（suite `podcast`）由 `publish.py` 的 `run_all(payload, suite=system.suite)` 擋著，會擋發布。**有在保護東西。**
- **manifest 層 11 條**（suite `podfetch`）只有人手動跑才會執行。**沒有在保護任何東西。**

拿今天的 manifest 手動跑一次，它立刻抓到東西：

```
FAIL  podfetch.no_block_repetition  3 處整段重播
      bloomberg-1000784374002.md 281 token @1664→2582
      iltb-1000784008514.md 970 token @7041→8000／959 token @7041→8959
WARN  podcast.completeness_band     iltb = 1.57
9 PASS · 1 WARN · 1 FAIL
```

**它抓得到，只是沒有人問它。** 這跟 `scripts/podcast/healthcheck.py`（44KB、同樣沒人呼叫）
是同一種東西，而且是最糟的那一種狀態 —— 不是沒有，是有但不會響。
兩者要一起決定：接到 `kbwatch` 上，或搬進 `_attic` 並寫下理由。**留著不呼叫是最糟的第三種。**

### 通則

今天第七次撞到同一族的錯，但這次的形狀更窄一點，值得單獨記：

> **守衛的維度必須低於它宣稱保護的東西。**
> `written` 從 `eps` 數出來，就永遠說不出 `eps` 的任何事情；
> 位元組數量得到「整份垮掉」，量不到「少一集」；
> `last_run_utc` 是視窗起點，說不出「今天有沒有跑」。
> 每一條守衛都要問一次：**它讀的東西，跟它宣稱在防的東西，是同一個來源嗎？**

還有一條更短的：**「這個檔案存在」與「這個檔案會被執行」是兩件事。**
`podcast_verify.py`、`healthcheck.py` 都寫得很好，都在 repo 裡，都沒有在跑。
`grep -rn <檔名>` 一秒鐘的事，而它問的是「除了我自己，誰在叫它」。

## 2026-08-20 夜｜⑤ 定案：接上，不進 _attic —— 而它一接上就問出兩個新問題

先前把 `healthcheck.py`（891 行）跟 `podcast_verify.py` 一起歸類成「留著不呼叫」，
打算二選一：接到 kbwatch，或搬進 `_attic`。**跑一次它就知道不能搬。**

### 它跟 `checks/podcast.py` 不是重疊，是互補

檢查程式刻意**不做 IO**，只看當天那一份 payload；healthcheck **全部都是 IO**：

| | `checks/podcast.py`（16 條） | `healthcheck.py` |
|---|---|---|
| 範圍 | 當天那一份 payload | 20 天全部日檔、repo、線上站台 |
| IO | 不做 | 全部 |
| 由誰跑 | doc 層 6 條由 `publish.py` 擋著 | 先前沒有人跑 |

它抓到三樣我以為沒實作的東西：

- **`推送鏈 local 與 origin 同雜湊`** —— 就是 `.kb-data-repo`、`index.html`
  那種「改了但 `git add data` 沒帶到」的偵測器。
- **`線上狀態`** 連 GitHub Pages —— 舊規格的 cache-buster 實地驗證。
  我先前判斷「我們的失敗形態跟舊系統不同，這個儀式不必照搬」，
  **那個判斷是對的，但結論下錯了**：不必照搬的是儀式，不是那條驗證，
  而那條驗證一直都在，只是沒有人叫它。
- `index.json 對應`、`觀察點記分板`、20 天日檔可解析。

### 接上去之後才發現的兩件事

**一、它今天不會抓到 `fwdguidance`。** 它的 CSS 對帳是「資料**用到**的 22 個
showKey 都有色條」——fwdguidance 還沒出過集數，不在那 22 個裡。
**「加了節目卻忘了加色」恰好只發生在還沒出集數的那段期間**，
所以這條檢查對它唯一會發生的時機是盲的。補上反方向：`shows - bar`。

**二、`shows.json` 有兩份，沒有任何東西在對帳。**
podfetch 執行時讀的是 `~/.podfetch/shows.json`（`podfetch.py` 的 `SHOWS_PATH`），
版控那份在 `kb-core/scripts/podcast/`。不同步的樣子是**什麼都沒發生**——
版控那份加了一檔節目，podfetch 照舊不去抓，日報少一檔，
而所有檢查都是綠的，因為每一條都只讀得到其中一份。

**我今天早上就是拿版控那份算出「21 檔現役」，據此判 fwdguidance 缺 CSS。
那個結論的前提是兩份一樣，而當時沒有任何東西在保證這件事。**
結論後來是對的，但那是運氣。補上 `check_shows_sync`。

兩條新檢查都被 `~/.podfetch` 擋在沙箱外，所以沙箱那次執行**對它們什麼都沒證明**。
另外拿 fixture 逼出五種情形（兩份一致／版控多一檔／內容有差／現行 index.html 不該叫／
加一檔無色節目要叫），五種都對，才算數。

### 接法

`launchd/kbwatch-podcast.sh` 一支 shell 跑兩件事，退出碼取較差的那個。
**不塞進 `watch_sentinel.py`**：看門狗的依賴要比它守的東西少。
watch_sentinel 只需要 `git fetch`；healthcheck 需要網路、`~/.podfetch`、逐字稿目錄。
合併等於讓看門狗長出三個新的失敗點，任何一個壞掉都會讓看門狗自己變紅，
**把真正的訊號埋掉**。

排程釘整點（02／06／10／14／18／22）而不是照抄 advisory 的 `StartInterval 14400`：
watch_sentinel 任何時刻問答案都一樣，healthcheck 的答案跟時點有關，
而 `StartInterval` 的相位取決於載入時刻，遲早會漂到 03:00 的日報中間。

同時補上 `com.kenny.kbwatch.podcast` 這個看門狗本身——**podcast 的哨兵先前沒有人看**。
`watch.py` 存在的理由（GitHub 60 天無活動自動停用排程）對 podcast 一樣成立。
它今天才第一次成功，60 天還很遠——**而「還很遠」正是這種東西不會被補上的原因。**

### 通則

> **「這個檔案存在」與「這個檔案會被執行」是兩件事**，
> 而第二件事只要一行 `grep -rn <檔名>` 就問得出來：除了我自己，誰在叫它。

還有一條更難看見的：**接上一個沉睡很久的檢查，第一件事不是相信它的綠燈，
是問它「你這條是拿什麼算的」。** healthcheck 的 CSS 那條是綠的，
而它綠的理由（只看用過的 key）正好讓它對唯一會出事的時機視而不見。
