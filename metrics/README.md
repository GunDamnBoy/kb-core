# 七套系統的用量帳

`usage.csv` 一輪一列，**由 `tools/usage_report.py` 讀逐字稿算出來，不是抄回報的**。

## 為什麼不沿用 podcast 原本那四欄

`scripts/podcast/metrics-columns.md` 對來源寫得很誠實：**「人工，抄自當輪用量回顧」**。
那是自述——代理回報它**認為**自己用了多少，然後有人抄進 CSV。
而代理看不到自己的 usage 欄位，只能估。

> **自述與量測在 CSV 裡長得一模一樣，而只有一個能拿來做決定。**

**這份 CSV 只收量測出來的列。** podcast 2026-08-22 之前那幾輪的數字是自述的，
留在 `scripts/podcast/metrics.csv`，**不要搬過來** ——
搬過來之後就再也分不出哪幾列可以信。

## 有效 token 的權重只有一個家

重讀 ×0.1、寫入 ×2、產出 ×5、新輸入 ×1 —— 寫在 `usage_report.py` 的 `W`。
七套共用，不然「這輪比上輪貴」會變成「兩邊用了不同的尺」。

## 怎麼比

**比效率看 `subagent_tokens_k ÷ 工作量`**（podcast 用逐字稿 KB、research 用份數），
不要用 `eff_tokens_k ÷ 件數` —— 後者混了固定開銷與當場的維護動作。
這一條是 podcast 2026-08-15／08-17 兩次踩出來的，逐字適用於其他三套。

## 欄位

| 欄 | 意思 |
|---|---|
| `date` | 那一輪自己的日期（台北）。由呼叫端用 `--date` 明講 ——
sidecar 帶的 `date`、掃描查的那一天，兩條路都知道。
**沒給才退回逐字稿最後一筆的日期，而那是 UTC**：整輪在台北 08:00 前收工的話
（podcast 03:00、broker-research 有時凌晨），`last` 仍在前一天的 UTC，
那一列會記成前一天 —— **而它會跟前一天那一套真正的列撞在一起**。
2026-08-24 的回歸測試踩到過，當天修掉。
`started_at`／`ended_at` 仍然是 UTC，所以台北早上起跑的那幾輪，
`started_at` 會落在 `date` 的前一天，**那是預期的，不是錯的** |
| `system` | `usage_report.py` 的 `SYSTEMS`：`advisory`／`chart`／`podcast`／`broker-research`／`bubble`／`convergence`／`houseview`。**值域擋在程式裡** —— 打錯一個字會變成一套從此只有一列的「系統」 |
| `started_at`／`ended_at` | **切界線之後**，主線逐字稿的第一筆與最後一筆，UTC 的 `Z`。
只看主線：子代理跑在主線等待的那段裡面，不會把跨距撐大 |
| `minutes` | 兩者相差幾分鐘。**這一欄問「這一輪實際在動多久」，不是「界線給了多久」** ——
界線是輪次宣告的，跨距是量到的，兩者的落差本身就是資訊（輪次早收工，或界線切得太鬆）。
2026-08-24 之前的列沒有這三欄，**留空不補 0**：`0.0` 看起來像量到了一個瞬間完成的輪次 |
| `eff_tokens_k` | 主線＋子代理的加權合計 ÷ 1000 |
| `main_turns` | 主線帶用量的輪次 |
| `subagents`／`agent_turns` | 子代理個數與來回總和 |
| `subagent_tokens_k` | 子代理加權合計 ÷ 1000 |
| `out_tokens_k`／`cache_read_k`／`cache_write_k` | 未加權的原始數，用來看結構往哪偏 |
| `bounded` | **這個數字能不能拿來做決定 —— 而且是靠哪一種上界。**
`no` ＝ 沒切界線，那份逐字稿若同時裝了維護對話，算出來的是兩者之和。
其餘四種是上界的出處，**可信度由高到低**：
`sidecar`（輪次自己寫的交草稿時刻）、
`window`（日檔裡的 `window.to`，與前者是同一個值的兩條路，發布後不可改寫）、
`commit`（日檔那一天最早的那顆 commit ——**那是 publish 成功的時刻，不是交草稿的時刻**）、
`manual`（有切，但沒人說得出那個時刻哪來的）。
**不是同一種出處的列不要直接相比**：2026-08-24 的 advisory 用 `window` 是 29,431k／99 輪，
用 `commit` 是 36,030k／184 輪 ——**差 22%**，因為那天 publish 被一個沒提交的工作區
擋到 10:04。平常 `commit` 只比 `window` 晚一兩分鐘，**所以它壞掉的那天不會有人發現**。
2026-08-22 的 broker-research（43,339k／617 輪）是 `no`，用的是一場維護對話的逐字稿，
**不要拿它當週報成本** |
| `transcript` | 量的是哪一份 —— **挑錯逐字稿與挑對的，數字都很合理** |
