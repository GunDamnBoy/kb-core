# 文件分工與系統形狀

第 1／2 步查漂移時對照用。標**唯一正本**的地方沒有副本——任何看起來像副本的東西就是漂移。

| 檔案 | 只放什麼 | 誰讀 |
|---|---|---|
| `AGENT_BRIEF.md` | 現在的規格與判斷規則、單期 JSON schema、上游庫清單與各庫性質及計票規則（第 0 節的表）、**「一組要一起改」清單的唯一正本**（第 3.0 節末） | 每週排程完整讀一次 |
| 排程 prompt | 流程骨架（與 `MAINTENANCE.md` 第 3 節**逐字同一份**） | 排程執行時 |
| `MAINTENANCE.md` | 維護流程（第 2 節）、排程 prompt 正本與 cron（第 3 節）、已知的坑、待辦、事故與決策檔案 | 維護者 |
| `CHANGELOG.md` | 逐版變更、度量趨勢、失效模式目錄、回溯要點 | 維護者 |

新的事實細節寫 brief；新的「為什麼」寫 MAINTENANCE 或 CHANGELOG。**執行視野**只有 brief 與 prompt 兩份——要生效的規則就得落在這兩份裡。

資料檔：`data/index.json`（封存索引、最近三期與量化快照）、`data/calls.json`（訊號帳本：戰績與未結案帳目）、`data/upstream.json`（上游指紋基準）。`data/YYYY-MM-DD.json` 是每期封存，只讀不改。

## 系統形狀

多個獨立知識庫互相看不到對方，疊起來才看得到四種訊號：**三方共振**（三個獨立聲音）、**關鍵背離**（核心價值）、**共識裂縫**（掛在 item 上的 tag，不是章節）、**單邊訊號**（只標記不判斷）。

兩個跨期累積機制：**訊號帳本**（可證偽判斷登帳 → 下期逼驗收 → 站台記分板）與**上游改版偵測**（監控庫指紋 diff，開工前在 `PREP.md` 頂部亮 🛑）。

排程 taskId `convergence-weekly`，每週日晚間跑；推送由 `com.kenny.dashpush` 每 180 秒自動完成。

## 上游介面

投顧庫（v17／v18 起）的每日 JSON 與其 `data/index.json` 各日 entry 帶機器可讀欄位，**跨庫比對可以直接吃**：卡片 `thread`（跨日主題連續劇代號，取代跨日字串比對）、`overview.pulse`（五資產每日立場，翻轉本身就是敘事訊號）、`overview.watchReview`（昨日盯盤節點應驗／落空／未決，是上游自己的驗證戰績，可與本系統帳本互驗）、`thermo` 數值日序列與 `snap` 數值鏡像。

正本規格在投顧 repo 的 brief 第 3.5 節，本檔只記「它們存在」。是否納入計票規則由當期維護決定，並寫進本系統 brief 第 0 節。
