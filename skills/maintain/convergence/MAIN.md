# 主題匯流訊號報 · 維護

它不產出資訊，它產出**訊號的合成**：多個互相看不到對方的上游知識庫，疊起來才看得到的東西。一期讀起來像「本週新聞回顧」就是失敗。訊號種類、跨期機制、文件分工與上游介面見 [`FILES.md`](FILES.md)。

全程繁體中文（台灣用語）。本機 `~/convergence-weekly`（沙箱掛載點腳本會自動偵測；讀不到就用 `request_cowork_directory` 連），站台 <https://gundamnboy.github.io/convergence-weekly/>。

## 正本與複本

系統的每個意義都有**正本**，本檔不持有會隨版本**漂移**的值——來源清單與數量、字數門檻、章節數、cron 字串、檔案清單、檢查項目明細，一律以 repo 內文件為正本。本檔只放三件事：讀哪些正本、怎麼比對、哪些不變式不能鬆。本檔與 repo 文件矛盾時**以 repo 文件為準**，並在收工時用 save_skill（overwrite: true）更新本檔——直接改快取檔不會生效。

## 硬規矩

- **本機 repo 看狀態只用 `cat`／`ls`／`grep`**：dashpush（`com.kenny.dashpush`）每 180 秒自動推送，任何 git 指令（含 `git status`）都會留下 `.git/index.lock` 擋死它。沙箱 clone 的複本不受此限。
- **發布只走 publish.py**：草稿一律寫 `work/`，publish.py 一條指令收尾（它自己編 index、跑 verify、搬檔）。檔案一進 `data/` 就等於發布——這是發布閘門整個設計的前提。
- **`data/YYYY-MM-DD.json` 只讀不改**：歷史永不改寫，發布後才發現的問題走 `errata`。
- **cron 以台北本地時間寫**（不是 UTC）；正確字串以排程任務本身與 `MAINTENANCE.md` 第 3 節為準，兩者逐字一致。
- **訊號稀薄的一期就照實寫**：真沒有背離就寫「本週高度一致，這本身是訊號」，章節據實留白。

每條規矩的來歷與其他歷史坑在 `MAINTENANCE.md`，重複踩過的失效模式在 `CHANGELOG.md` 的失效模式目錄。

## 第 1 步：載入現況

1. 跑 `python3 ~/convergence-weekly/healthcheck.py`（唯讀、不碰 git；加 `--metrics` 另印度量）。FAIL 與 WARN 全部帶進報告。
2. 讀 `MAINTENANCE.md` 全文（含待辦與事故檔案）。
3. 讀 `AGENT_BRIEF.md` 全文。
4. 讀 `CHANGELOG.md` 最新一版全文＋版本索引表（回溯或跨版比較時才讀更早的）。
5. 用 `list_scheduled_tasks` 找 `convergence-weekly`，記 cron／enabled／nextRunAt／lastRunAt，並 Read prompt 全文。
6. 讀 `data/index.json`（最近三期與量化快照）、`data/calls.json`（戰績與未結案帳目）、`data/upstream.json`（指紋基準在不在）。

healthcheck 跑過的項目就用它的輸出，涵蓋範圍以它印出來的內容為準。

完成條件：六項都有實際輸出在手，沒有一項靠記憶或推論。

## 第 2 步：找漂移

healthcheck 只抓機械式不一致，敘述性矛盾只能靠讀。**固定用 Agent 子代理獨立比對**——歷次維護的子代理複查命中率極高（CHANGELOG 有統計）。給子代理的要求：指出行號與原文、只回報不一致處、指明哪一邊是對的，回報就是產出。

**漂移**＝某個意義偷偷長出第二份，或兩份正本各說各話。逐面向查，每面向給出「相符／漂移／不適用」；判為漂移的要指出兩邊差在哪、哪一邊是對的。各面向的正確值以 repo 文件為準。

**排程 prompt ↔ brief ↔ 實作**

- 流程步驟與分支判斷（備料的不產期分支、樣本偏薄、上游改版 🛑、帳本結案）兩份是否一致
- 發布路徑：草稿寫 `work/`、publish.py 一條指令收尾、exit 語意
- calls 登帳準則（id 格式、claim＋judge 必填、result 值域、void 的定位）
- 交付訊息的行數與內容
- prompt 有沒有遺漏 brief 的關鍵規則
- 規則有沒有落在**執行視野**內：每週排程執行時讀得到的只有 brief 與 prompt，規則寫在 CHANGELOG 或 MAINTENANCE 等於沒生效（CHANGELOG 記錄過的重複失效模式）

**四條正確性不變式（每一份文件裡都維持原狀）**——它們看起來像效率或風格問題，實際上都是正確性問題：

- 兩個敘事子代理**平行且互相看不到對方**（一鬆，「共振」就變自我實現的預言）
- 合成順序**先量化後敘事**（反了就找不到背離）
- 量化佐證只取 `events` **以外**的來源（events 是 Google News，與各庫**同源**，同一則新聞會被數兩次）
- **投顧與圖表計為同一票**（圖表庫選題與投顧**同源**）

**brief 內部自我一致性**：數值打架、上文被下文取代沒改、待決事項已解決沒劃掉、schema 與實作是否同步。「一組要一起改」的清單以 brief 第 3.0 節末為**唯一正本**（MAINTENANCE 刻意不複寫）。

完成條件：三組面向逐項都有判定，判為漂移的都附行號與原文；四條不變式在 brief 與 prompt 兩份裡逐條確認過。

## 第 3 步：報告現況，再問要改什麼

報健檢結果（FAIL／WARN 逐條，PASS 一行）、排程狀態、最近三期與跨期趨勢點數、**帳本戰績**、第 2 步的漂移清單（具體指出哪邊對）、MAINTENANCE 的待辦。

完成條件：使用者看完報告、指定了要改什麼，且你把它覆述成一句話得到確認（使用者已明示授權執行者時，覆述的對象是那份授權）。這一步的產出是報告與那句話，不是任何檔案修改。

## 第 4 步：執行修改

拿到第 3 步的確認之後，讀 [`MODIFY.md`](MODIFY.md) 並照它走——改哪個檔、schema「一組一起改」、排程 prompt 整份取代與兩處同輪同步、新增比對來源的第一個問題、CHANGELOG 該寫的四項，以及改完必須全數通過的驗證清單。
