## 排程 SKILL.md

它對檔案工具唯讀，只能走 `update_scheduled_task`，而 `prompt` 是**整份覆寫**：先 Read 目前檔案，以它為基礎修改後送出完整內容。拿記憶中的版本重寫＝覆寫事故（來歷見 `MAINTENANCE.md` 第 7 節）。

**覆寫時不要順手改內容。** 上面那條擋得住「拿記憶重寫」，**擋不住「一邊貼一邊多寫一句」** —— 那等於在同步的動作裡製造新的漂移。要改內容就先改正本、重讀、再整份貼。**流程是「正本改完 → Read 正本 → 原封不動貼過去」，貼的那一步不做任何編輯。**

## 新增檢查

新增任何檢查時，先問「正常情況會不會也觸發」。**要求兩個獨立訊號同時成立才報**——單獨看必然有雜訊的訊號被當成獨立判準，初版就會對 9 集報 8 集、對 72 集報 15 集。能寫成條件的判斷就寫成條件，叮嚀會被忽略。

**動到 `kb-core/tools/` 或 `kbcore/` 的共用程式時，先數有幾套系統吃它。** 那些檔案不屬於任何一套系統——`tools/publish.py` 被**五支** `kbpublish` plist 共用，而每一套的 `staged_paths` 形狀不同。2026-08-24 加發布前工作區檢查時，我把 `staged_paths` 一律當目錄處理，於是投顧的 `["data", "index.html"]` 裡那個**檔案**被判成外人，會讓投顧發布每 60 秒失敗一次；podcast 這一側完全正常，所以在 podcast 的情境裡怎麼測都測不出來。**是複驗子代理去讀 `systems/*.py` 才抓到的。**

兩條可操作的規矩：

- **`grep -rn "staged_paths=" systems/*.py` 是一行的事**，改共用程式前先跑，把每一種形狀都列進測試案例。同型的還有 `index_entry`／`index_meta`／`republish_rule`。
- **不要在註解裡寫「這不可能讓事情更糟」。** 那句話是強度最高的宣稱，而寫它的當下你數的是「我測了幾個案例」，不是「有幾種輸入形狀」——**兩者的差就是漏掉的那一種**。要寫就寫它在什麼條件下成立。

## 驗證

**全數通過才算完成**；任何一項失敗就回上一步。

1. 重跑 `python3 ~/kb-core/scripts/podcast/healthcheck.py`，確認沒有新的 FAIL。**在沙箱裡跑時，`shows.json 兩份`／`節目在文件裡`／`podfetch` 三條會固定 WARN 跳過，等於沒驗到**——動過那三條涵蓋的東西就要在 Mac 上再跑一次。
2. **再叫一次子代理**照 [`SYNC-CHECKLIST.md`](SYNC-CHECKLIST.md) 獨立比對，確認這次改動沒有製造新的不同步、沒有弄丟關鍵規則、也沒有覆寫掉別場維護的成果。若這次改了任何指標、門檻或因果宣稱，明確指定子代理去讀程式確認那個值實際接到哪條分支——文件對讀查不出「理由寫錯」這種矛盾。
3. 這次新增的任何量測或自動化，當場驗證它回傳非空結果（空值與 0 都算失敗）。
4. ~~收工快照~~（2026-08-22 退役）。改成確認 kb-core 推得出去：`tail -5 ~/outbox/kbcorepush.log`。**若看到「檢查自檢有失敗的條目」就是新加的檢查沒過 `fixture`／`near_miss` 契約，它會擋住之後所有 kb-core 推送**——`fixture` 要能觸發檢查（非 PASS），`near_miss` 要剛好通過（PASS），兩者方向相反，很容易寫反。
5. 驗線上狀態時，網址帶 cache-buster 並確認 `updatedLabel`。
6. **收工前確認 `~/podcast-knowledge-digest` 工作區乾淨**——**收工前重跑一次**
   `healthcheck.py`，看 **`工作區` 那一條**。它 **WARN 且具名列出檔案**時，
   在本場結束前把那些檔提交或 stash，**不要留給明天**。
   （讀不到 `.git/index` 時它也會非 PASS，但那是「跳過」不是「有髒檔」，沒有東西可提交。）
   理由：`publish.py` 對 podcast 只 stage `data/`，repo 根目錄改過而沒提交的檔永遠 commit 不掉，
   而 `git pull --rebase` 要求工作區乾淨——隔天 03:00 的發布會整個被擋住。
   **判準綁在收工前那一次 healthcheck**，因為髒檔通常是本場在第 1 項之後自己改出來的。
   **任何人、任何場次動了非 `data/` 的檔，當場提交**（`MAINTENANCE.md` 第 6 節）；本項是最後一道。
   **不要用 `git status` 代替它**——`check_worktree()` 純讀檔正是為了不碰鎖；
   真的非跑 git 不可時，照 `MAIN.md` 硬規矩第一條的條件路徑走。

   > **要手動 `git push` 的話，`工作區 PASS` 還不夠**（2026-09-17 實地踩到）。
   > 那一條刻意排除 `data/`，前提是「publish 會 stage 它」—— **而 publish 只在
   > `~/outbox/podcast/` 有草稿時才跑**。維護場改了 `data/observations.json`、
   > 當天的草稿又已經被消化掉時，那個檔沒有任何排程會提交它，
   > 於是 healthcheck 報 PASS，而 `git pull --rebase` 當場回
   > `cannot pull with rebase: You have unstaged changes`。
   > **手動推之前一律先 `git status --short` 看一次**，`data/` 底下的也要提交。
   > （`check_worktree()` 已於同日改成會把 `data/` 底下的髒檔列出來、但不計入 WARN。）
   >
   > **而且順序是先 rebase 再 push**：origin 上有 `sentinel.yml` 與 `deploy.yml`
   > 兩支 workflow 會自己 commit，所以 local 幾乎必定落後。
   > publish 每天都做 `pull --rebase`，**所以它從來不會撞到這個，只有人會**。
